# Banco Ágil - API Contract

**Version:** 1.0
**Base Path:** `/api/v1`
**Reference Documents:** PROJECT.md, REQUIREMENTS.md, ARCHITECTURE.md, STATE_MACHINE.md, DECISIONS.md, internal/TEST_PLAN.md
**Status:** Ready for Backend and Frontend Implementation
**Purpose:** Define the stable HTTP contract between the FastAPI backend and the React frontend.

---

## 1. Purpose

This document defines the public API contract for the Banco Ágil application.

The API must allow the React frontend to interact with the banking agent system without knowing internal architecture details such as LangGraph nodes, internal services, CSV repositories, LLM providers, or StateGuard mechanics.

Core principle:

```txt
The frontend renders the conversation.
The backend owns state, rules, orchestration, and decisions.
```

---

## 2. API Design Principles

1. HTTP is stateless, but the backend conversation is stateful through `session_id`.
2. The backend is the authority for session state.
3. The frontend must never infer business logic from internal states.
4. All responses must include `trace_id` for debugging and support.
5. User-facing errors must be friendly.
6. Internal implementation details must not leak to the frontend.
7. Response contracts must remain stable once frontend implementation starts.
8. All timestamps must use ISO 8601 format.
9. All endpoints must return `application/json`.
10. No endpoint may expose API keys, LLM prompts, raw provider responses, or full sensitive customer data.

## 4. Required Headers

## 4.1 Request Headers

All JSON requests must include:

```txt
Content-Type: application/json
```

Optional correlation header:

```txt
X-Trace-ID: uuid-v4
```

Rules:

* If the frontend sends `X-Trace-ID`, the backend may reuse it if valid.
* If missing or invalid, the backend must generate a new `trace_id`.
* The `trace_id` must be returned in the response body.

---

## 4.2 Response Headers

Recommended:

```txt
Content-Type: application/json
X-Trace-ID: uuid-v4
```

---

## 4.3 Session ID Rules

Session IDs must be generated by the backend.

Rules:

* Session IDs must use UUID v4 or an equivalent cryptographically safe random identifier.
* Session IDs must not be sequential, guessable, or derived from CPF, timestamp, customer name, or IP address.
* The frontend must treat `session_id` as an opaque value.
* The frontend must not parse, modify, or infer meaning from `session_id`.
* A new session must start unauthenticated.

## 5. Public Types

## 5.1 Public Agent Labels

The API may expose only public-safe agent labels.

Allowed values:

```txt
triage
credit
credit_interview
exchange
system
```

Rules:

* The API must not expose internal node names such as `triage_node`, `intent_node`, `ending_node`, or LangGraph internals.
* `system` may be used for errors, session reset, or generic messages.

Allowed values:

Rules:

* Public states are not required to match internal LangGraph state names one-to-one.
* The frontend may display generic status based on `state`, but must not use `state` to perform business decisions.

## 8. Endpoint: Chat

## 8.1 Request

```txt
POST /api/v1/chat
```

Body:

```json
{
  "session_id": "optional-session-id",
  "message": "Quero consultar meu limite"
}
```

Schema:

```txt
session_id: string | null | optional
message: string, required, min length 1, max length 2000
```

Rules:

* If `session_id` is missing, the backend must create a new session.
* If `session_id` exists and is valid, the backend must continue the session.
* If `session_id` is expired, the backend must return a controlled response requiring a new authentication flow.
* Empty or whitespace-only messages must be rejected.

---

## 8.2 Success Response

Status:

```txt
200 OK
```

Body:

```json
{
  "session_id": "1a6b6ec7-90b7-4c5d-a373-18c81004c4f7",
  "reply": "Claro. Antes de continuar, preciso confirmar seu CPF.",
  "agent": "triage",
  "state": "ASKING_CPF",
  "ended": false,
  "trace_id": "2f4a3479-9e34-4c78-b6ce-476abf879789",
  "metadata": {
    "recoverable": true,
    "retry_available": false,
    "suggested_action": "continue"
  }
}
```

---

## 8.3 Chat Response Schema

```txt
session_id: string
reply: string
agent: PublicAgentLabel
state: PublicConversationState
ended: boolean
trace_id: string
metadata: ChatMetadata | null
```

`metadata` schema:

```json
{
  "recoverable": true,
  "retry_available": false,
  "suggested_action": "continue | retry | reset | reauthenticate | none",
  "last_action_summary": "ACTION_NAME | null",
  "adherence_flag": false
}
```

Personalization rule:

* User-facing personalization, such as greeting the authenticated customer by name, must be rendered by the backend inside `reply`.
* The API must not expose `customer_name` in `metadata` for V1.
* This keeps the frontend as a thin renderer and avoids unnecessary customer data exposure.

Allowed `suggested_action` values:

```txt
continue
retry
reset
reauthenticate
none
```

Rules:

* `reply` must always be user-facing.
* `reply` must not expose internal exceptions.
* `agent` must use public labels only.
* `state` must use public-safe states only.
* `metadata` must not contain internal stack traces, prompts, or raw provider data.
* `reply` must be derived from the final `GraphState.last_assistant_output` for the current turn.
* If `system_bridge_message` was consumed during the turn, it must already be included in `reply`.
* The API must not return `system_bridge_message` as a separate field.

## 8.8 Recommended Authentication Sequence

The triage flow requires three turns to complete authentication from a new session:

1. Send any first message without `session_id`. The backend creates a new session and replies with `state: ASKING_CPF`.
2. Send the customer's CPF with the returned `session_id`. The backend replies with `state: ASKING_BIRTH_DATE`.
3. Send the birth date (`DD-MM-YYYY`) with the same `session_id`. On success, the backend replies with `state: AUTHENTICATED`.

The frontend must persist the `session_id` returned from step 1 and include it in all subsequent requests.

## 9. Endpoint: Reset Session

## 9.1 Request

```txt
POST /api/v1/sessions/reset
```

Body:

```json
{
  "session_id": "1a6b6ec7-90b7-4c5d-a373-18c81004c4f7"
}
```

Body is optional. If omitted, backend creates and returns a new clean session.

Schema:

```txt
session_id: string | null | optional
```

---

## 9.2 Success Response

Status:

```txt
200 OK
```

Body:

```json
{
  "message": "Session reset successfully",
  "session_id": "8d61df90-7b0f-4c16-87d8-7e5721af9a11",
  "state": "STARTED",
  "ended": false,
  "trace_id": "68c8786d-a777-4597-a653-069fbb17fc38b"
}
```

Rules:

* The backend must invalidate the previous session when possible.
* The backend must return a new `session_id`.
* The frontend must replace its stored session ID with the response `session_id`.
* Reset must not preserve authentication status, temporary domain data, or recent messages.
* Reset must be idempotent from the frontend perspective: calling reset multiple times should always result in a clean usable session.

## 10.3 Resume Rules

* Blocked sessions may return `ended=true`.
* `recent_messages` must contain at most the latest 3 turns.
* Sensitive data should be minimized.
* The endpoint must not expose `GraphState` directly.
* The endpoint must not expose CPF unless explicitly justified. V1 should avoid exposing CPF.
* In V1, missing sessions return `SESSION_NOT_FOUND`; TTL expiration is out of scope.

## 11. Standard Error Response

All controlled errors must follow the same shape.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Não consegui processar essa informação. Confira os dados e tente novamente.",
    "trace_id": "2f4a3479-9e34-4c78-b6ce-476abf879789",
    "recoverable": true,
    "suggested_action": "retry"
  }
}
```

Schema:

```txt
error.code: ErrorCode
error.message: string
error.trace_id: string
error.recoverable: boolean
error.suggested_action: continue | retry | reset | reauthenticate | none
```

Rules:

* Error responses must not include stack traces.
* Error responses must not expose internal class names.
* Error responses must not expose provider raw responses.
* Error responses must not expose secrets.

## 12. HTTP Status Code Policy

| Status | Meaning               | Usage                                                |
| ------ | --------------------- | ---------------------------------------------------- |
| 200    | OK                    | Successful chat, reset, resume, health               |
| 400    | Bad Request           | Malformed semantic request not covered by schema     |
| 404    | Not Found             | Session not found or optional route resource missing |
| 409    | Conflict              | State conflict, blocked session, transition denied   |
| 422    | Unprocessable Entity  | Pydantic/schema validation error                     |
| 423    | Locked                | CSV lock timeout or resource temporarily locked      |
| 500    | Internal Server Error | Unexpected backend failure                           |
| 503    | Service Unavailable   | Critical dependency unavailable                      |

Rules:

* Normal user input mistakes inside the conversation should usually return `200 OK` with a clarifying `reply`, not HTTP errors.
* HTTP errors are reserved for API-level or infrastructure-level failures.

## 13. Error Code Mapping

| Error Code              | HTTP Status | Recoverable | Suggested Action |
| ----------------------- | ----------: | ----------- | ---------------- |
| VALIDATION_ERROR        |         422 | true        | retry            |
| SESSION_NOT_FOUND       |         404 | true        | reset            |
| SESSION_EXPIRED         |         409 | true        | reauthenticate   |
| AUTH_FAILED             |         200 | true        | retry            |
| AUTH_BLOCKED            |         409 | false       | reset            |
| STATE_TRANSITION_DENIED |         409 | true        | continue         |
| CSV_READ_ERROR          |         500 | false       | reset            |
| CSV_WRITE_ERROR         |         500 | true        | retry            |
| LOCK_TIMEOUT            |         423 | true        | retry            |
| LLM_PROVIDER_ERROR      |         503 | true        | retry            |
| EXCHANGE_PROVIDER_ERROR |         200 | true        | continue         |
| MISSING_DATA_FILE       |         503 | false       | none             |
| INTERNAL_ERROR          |         500 | false       | none             |
| CORRUPTED_DATA_FILE     |         503 | false       | none             |

Notes:

* `AUTH_FAILED` is usually part of the conversational flow and should not be returned as HTTP error.
* `LLM_PROVIDER_ERROR` should be hidden from the user if deterministic fallback succeeds.
* `EXCHANGE_PROVIDER_ERROR` should produce a friendly chat reply when possible.
* If LLM providers fail but deterministic fallback succeeds, no `LLM_PROVIDER_ERROR` is returned to the frontend. The response remains `200 OK` as a normal chat response.
* `SESSION_EXPIRED` is reserved for future TTL support and should not be emitted in V1.

## 14. Frontend Integration Rules

The frontend must follow these rules:

1. Store `session_id` only for UX continuity.
2. Always send `session_id` back if available.
3. Render `reply` as the source of truth for assistant message.
4. Disable input while waiting for `POST /api/v1/chat` response.
5. Show contextual loading messages when possible.
6. If `ended=true`, disable chat input and show a new session button.
7. If `suggested_action=reset`, show reset/new session option.
8. If `suggested_action=reauthenticate`, guide user back to authentication.
9. Do not infer business decisions from state.
10. Do not expose trace details to user by default, but allow copying `trace_id` for support if useful.

Forbidden frontend behavior:

* Calculating score.
* Validating credit approval.
* Reading or writing CSV.
* Calling LLM providers.
* Calling exchange providers directly.
* Hardcoding state transitions.
* Displaying internal node names.

## 15. Loading and UX Contract

Because LLM and exchange calls may introduce latency, the frontend should support contextual loading states.

Examples:

```txt
Analisando sua solicitação...
Consultando seus dados...
Verificando limites disponíveis...
Buscando cotação atual...
Atualizando sua análise de crédito...
```

Rules:

* Loading messages must not mention Grok, OpenAI, fallback, LangGraph, nodes, or internal providers.
* If response takes longer than expected, frontend may continue showing a neutral loading indicator.
* Backend does not need to stream responses in V1.

## 16. Security and Privacy Rules

1. API keys must never be returned by any endpoint.
2. Full CPF should not be returned by API unless explicitly required.
3. Error responses must not include stack traces.
4. `trace_id` is safe to expose.
5. `session_id` must be treated as opaque.
6. Frontend must not store sensitive customer profile data beyond what is needed for the current UI.
7. Backend logs should mask sensitive identifiers when possible.
8. Customer name should not be exposed as a separate metadata field in V1.
9. If personalization is needed, the backend should include it directly in the `reply`.
10. Session IDs must be opaque and non-guessable.

## 19. Contract Test Requirements

The backend must include tests validating:

1. `GET /api/v1/health` returns expected schema.
2. `POST /api/v1/chat` accepts request without `session_id`.
3. `POST /api/v1/chat` returns `session_id`, `reply`, `agent`, `state`, `ended`, `trace_id`, and `metadata`.
4. `metadata` is present and is either `null` or follows `ChatMetadata`.
5. `POST /api/v1/chat` rejects empty message.
6. `POST /api/v1/sessions/reset` returns valid new session response.
7. Error responses follow standard error shape.
8. Public agent labels are valid.
9. Public states are valid.
10. `trace_id` is present in success and error responses.
11. No endpoint exposes raw internal `GraphState`.
12. `POST /api/v1/sessions/reset` always returns a new usable `session_id`.
13. New sessions start unauthenticated.
14. `session_id` is treated as opaque and never derived from customer data.
15. `metadata` does not expose `customer_name` or sensitive customer profile fields.

Contract tests must pass before frontend implementation begins.

## 20. Versioning Policy

V1 uses:

```txt
/api/v1
```

Breaking changes require a new version or coordinated frontend/backend update.

Breaking changes include:

* Removing response fields.
* Renaming response fields.
* Changing `agent` allowed values.
* Changing `state` meaning in a frontend-breaking way.
* Changing error response shape.

Non-breaking changes include:

* Adding optional metadata fields.
* Adding new public states if frontend treats unknown states safely.
* Adding optional endpoints.
